# Рабочий процесс СПИКЕРА

## Начало задачи

1. Убедись, что работаешь в Git checkout, а не в установленной или распакованной release-папке.
2. Посмотри `git status --short --branch`, `VERSION`, `docs/progress.md` и связанные записи `docs/decisions.md`.
3. Прочитай связанный участок `docs/architecture.md`, текущий код и тесты; формулируй критерий готовности до изменения.
4. Не затрагивай чужие незакоммиченные изменения. Ветка создаётся от актуальной основной ветки.

## Реализация

- Меняй минимальный участок и держи изменение вместе с тестом.
- Не объединяй исправление пользовательского запроса с несвязанным форматированием или миграциями.
- Если формат данных меняется, добавляй совместимую миграцию и тест старых данных.
- UI тестируй на разных размерах окна, когда менялась компоновка; тяжёлые операции проверяй на возможность отмены и безопасного закрытия.
- Для микрофона проверяй старт, фактическое поступление PCM, текстовую гипотезу, остановку и освобождение устройства.
- Для диаризации проверяй число участников, неопределённые интервалы, переименование и ручную коррекцию на коротком синтетическом контрольном аудио.
- Для моделей проверяй отсутствие модели, неверный/частичный архив и контрольную сумму; не загружай пользовательские веса в GitHub Actions.

## Проверка

Запускай относящиеся тесты, затем полный набор:

```powershell
python -m unittest discover -s tests -v
python -m compileall -q scripts tests
```

Дальше — специализированная проверка сборки Windows, Android или ручного сценария по `docs/BUILD_WINDOWS.md`, `docs/ANDROID_BUILD_RU.md` и `docs/RELEASE_CHECKLIST.md`. Если тест требует реального микрофона, локального сервера, модели или Windows-инсталлятора, так и укажи; не симулируй успешный результат.

## Перед PR

1. Проверь `git diff --check`, статус и полный diff.
2. Убедись, что не попали `.env`, ключи, логи, аудио, транскрипты, персональные пути, модельные веса, `.build-venv`, `build/` и `dist/`.
3. Обнови только документы, которые стали неверными или нужны для нового поведения.
4. В PR запиши цель, область влияния, тесты и их результаты, ручные проверки и ограничения.
5. Если менялись архитектура, политика хранения, модели или выпуск, укажи связанные документы и решения.

## Завершение

Активную незавершённую работу оставь в `docs/progress.md`; законченную убери. В итоговом сообщении разделяй, что изменено, что проверено и что осталось проверить на реальном устройстве.
