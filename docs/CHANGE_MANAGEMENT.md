# Управление изменениями СПИКЕРА

Этот документ задаёт общий порядок проектных правок: от понимания запроса до проверки, документации и выпуска. Он адаптирует `devkit-main` к Python/PySide6-приложению, Windows-сборке и отдельному Android-клиенту. Основные правила помощникам находятся в корневом `CLAUDE.md`; `AGENTS.md` подключает их для Codex.

## 1. Перед изменением

1. Проверь корень Git, ветку, состояние дерева и актуальную версию из `VERSION`; не редактируй установленную папку вместо репозитория.
2. Прочитай `docs/progress.md`, `docs/architecture.md` и связанные записи `docs/decisions.md`.
3. Определи ожидаемое поведение, затронутые модули, критерий приёмки, возможное влияние на данные, установку, Windows и Android.
4. Не переписывай сопутствующие части «заодно». При неясности спрашивай только о выборе, который меняет смысл, безопасность или необратимость работы.

## 2. Внесение изменений

- Исправление дефекта должно иметь тест или воспроизводимую проверку. Новая возможность должна иметь проверку основного сценария и отказного случая.
- Сохраняй границы компонентов: UI не должен дублировать правила модели/движка; распознавание речи, диаризация, ИИ-обработка и синтез речи остаются раздельными функциями.
- При изменении формата очереди, настроек, экспорта, хранилища или пути моделей явно сохраняй совместимость или добавляй миграцию и тест миграции.
- При изменении общего поведения платформы оцени отдельно Windows и Android. Перенос логики в Android не считается выполненным от того, что обновлена Windows-версия.
- Обновляй архитектуру при изменении потоков данных, границ модулей или контрактов; решения записывай отдельным ADR; инструкции пользователя меняй только когда изменился реальный сценарий.

## 3. Проверки

Запусти проверки, связанные с изменением, и затем стандартный CI-набор:

```powershell
python -m unittest discover -s tests -v
python -m compileall -q scripts tests
```

Для сборки, изменения моделей/пакетов, нативных библиотек, микрофона, UI или Android добавь специализированную проверку из `docs/BUILD_WINDOWS.md`, `docs/RELEASE_CHECKLIST.md` или `docs/ANDROID_BUILD_RU.md`. Укажи окружение и результат; физический микрофон, пользовательские модели и качество диаризации требуют отдельной ручной проверки.

## 4. Данные, безопасность и лицензии

- Не добавляй пользовательские аудио/видео, транскрипты, журналы, конфигурации с секретами, кэш, runtime, модельные веса, сборочные результаты и локальные абсолютные пути.
- Перед передачей данных во внешний ИИ показывай пользователю, что именно и куда отправляется; оставляй действие явным и отменяемым.
- Не расширяй правила сетевого доступа и не ослабляй проверку HTTPS/локальных адресов без отдельной проверки угроз и тестов.
- Для нового движка/веса задокументируй источник, лицензию, SHA-256, размер, место установки, требования к памяти и возможность установки/удаления; проверь право включать его в публичный пакет.
- Держи приватные данные вне тестовых фикстур. Используй синтетические и короткие контрольные данные.

## 5. Документы и решения

- Одно описание факта должно иметь одно основное место. `docs/architecture.md` — как система устроена; `docs/decisions.md` — почему выбрана такая схема; `docs/progress.md` — только активная работа и приоритеты; `docs/workflow.md` — рабочий процесс.
- Обновляй затронутые документы в том же PR, что и изменение. Не обновляй карту архитектуры для локальной правки, не меняющей устройство.
- Новое существенное решение записывай как следующий постоянный ADR. Изменённое решение не стирай: укажи новое решение и причину смены.
- `docs/progress.md` не является журналом чатов: завершённые пункты удаляй, историю оставляй Git.

## 6. Pull request и выпуск

1. Проверь полный diff, точечные тесты, стандартный CI и документацию.
2. В PR перечисли изменение, причину, риск для пользовательских данных/совместимости, команды проверок и ручные сценарии, которые действительно запускались.
3. Сборка установщика — только по `docs/BUILD_WINDOWS.md`; выпуск — по `docs/RELEASE_CHECKLIST.md`. Не называй сборку релизной, пока не проверены комплектность файлов, SHA-256, чистая установка, обновление и запуск модели.
4. `VERSION`, тег и релиз меняются только в рамках явно запрошенного релиза. Документационные изменения сами по себе не создают новую версию приложения.
5. Перед публикацией повторно проверь секреты, приватные данные, локальные адреса, аудиофайлы и веса моделей в изменённом дереве.
